# workspace-audit: エージェントが存在しない場合の手動手順

`.claude/agents/workspace-auditor.md` が存在しない場合に限り、このスキル自身が以下の手順1〜7を実行する。エージェントに委譲する場合はエージェント自身が同じ内容を実行するため、このファイルを読む必要はない。

## 1. 構成を把握する

```bash
git log --oneline -15
git branch -a
git worktree list
ls projects/
```

`README.md`・`AGENTS.md`・`projects/README.md` を読み、リポジトリが自称している方針を確認する。以降の調査は「方針と実態がずれていないか」を見る作業になる。

## 2. 抜け殻ディレクトリを探す

git追跡ファイルが1つも無いのに、ディレクトリだけ残っているプロジェクトを探す。過去に、ソースが失われて `node_modules` だけが130MB残っていた事例がある。

```bash
for d in projects/*/; do
  n=$(git ls-files "$d" | wc -l)
  echo "$n  $d"
done
```

追跡ファイル数が0のディレクトリが見つかったら、`du -sh` で実サイズを確認し、実体が未マージブランチ側にあるのか完全に失われたのかを `git log --all --oneline -- <path>` で確かめる。

（gitコマンドを含むループが実行環境で拒否される場合は、`git ls-files projects/<name>/ | wc -l` をプロジェクトごとに個別に実行すればよい。以降のループを含む例も同様。）

## 3. gitの滞留を調べる

未マージブランチとworktreeの滞留を、放置の度合いが分かる形で測る。

```bash
git fetch origin
for b in $(git for-each-ref --format='%(refname:short)' refs/heads refs/remotes/origin | grep -v HEAD); do
  echo "$b: $(git rev-list --left-right --count origin/main...$b 2>/dev/null | awk '{print $2" ahead / "$1" behind"}')"
done
git worktree list --porcelain
```

behindが大きいブランチは、統合するにせよ捨てるにせよ判断が要る。locked なworktreeがあれば、ロックを保持しているプロセスが生きているかも確認する。

## 4. Git hooks が実際に動いているか確認する

設定はされているのに動いていない、という状態を検出する。`core.hooksPath` は存在しないパスを指していても**何のエラーも出さずに黙って無効になる**ため、実在確認が必須。

```bash
p=$(git config --get core.hooksPath)
echo "hooksPath: ${p:-(未設定)}"
[ -n "$p" ] && { [ -d "$p" ] && echo "実在する" || echo "存在しないパスを指している（フックは動いていない）"; }
```

`core.hooksPath` はリポジトリ全体で1つしか持てないため、複数のプロジェクトがそれぞれフックを設定していると最後に設定したものが勝つ。フックを持つプロジェクトが複数ある場合は、勝っていない側のフックが無効になっていることを明示する。

## 5. 各プロジェクトの健全性を実測する

設定ファイルを読んで判断するのではなく、**実際にlint・テスト・ビルドを走らせて通ることを確認する**。各プロジェクトのREADMEに書かれたコマンドを使う。依存が未導入なら先に導入する（導入方法は各プロジェクトのREADMEに従う）。

結果は「通った / 落ちた」を、落ちた場合は出力の要点とともに記録する。ここで落ちたものは最優先の実害として扱う。

## 6. 設定の不整合とドリフトを調べる

- **スキルのテンプレートと配置済みファイルのずれ**: `.claude/skills/*/templates/` 配下と、対応する配置済みファイル（各プロジェクトや リポジトリルートの `.devcontainer/`・`.vscode/` 等）を突き合わせる。この差分検出用のスクリプトが `.claude/skills/*/scripts/` 配下に用意されていればそれを使う。無ければ主要な設定ファイルを個別に diff する
- **同種の設定ファイルの食い違い**: 複数プロジェクトにある同じ役割のファイル（`.gitignore`・`.devcontainer/Dockerfile`・`.vscode/settings.json` 等）を比較し、一方にしか無い設定が意図的なものか調べる
- **推奨と実態の食い違い**: 設定が参照しているファイルが実在するか（例: `.editorconfig` を推奨しているのにリポジトリに無い）
- **gitignore の漏れ**: 生成物・キャッシュディレクトリが追跡対象になっていないか

```bash
git status --porcelain --ignored=no
git check-ignore -v <疑わしいパス>
```

## 7. 実害の大きい順に整理して報告する

見つかったものを3段階に分けて報告する。この分類は、対応の優先順位をユーザーが判断するためのもの。

1. **実害が出ているもの** — 既に壊れている・動いていないもの（テストが落ちる、フックが無効、ソースが失われている）
2. **ドリフト** — 正しい姿は分かっているのに追従できていないもの（テンプレート更新の未反映など）
3. **一貫性・ドキュメント** — 動作に影響しないが揃っていないもの（README の記載漏れ、CI 未整備、命名の不統一など）

各項目には、根拠（実行したコマンドと出力）と、対応する場合の方針を添える。**推測で「たぶん壊れている」と書かない**。確認できていないものは確認できていないと書く。

## 調査時の注意

- 調査のつもりで実行したコマンドが副作用を持つことがある（例: `uv run` は `.venv` を作る、`pnpm install` は `node_modules` を作る）。生成されたものは gitignore 済みか確認し、報告に含める
- ブランチの削除・worktree の削除・ファイルの整理は、このスキルでは行わない。判断材料を揃えてユーザーに渡すところまでが範囲
- リモートAPIのキャッシュ等で一時的に古い情報が返ることがある。「消したはずのものが残っている」ように見えたら、直接参照して再確認してから報告する（誤った修正を入れないため）
