# git-commit

main/masterに直接コミットが積み重なる、コミットメッセージの書式がバラバラ、コミットしたのにpushし忘れる——このスキルはその3つを機械的に防ぐためのものである。判断が要るのは「何を・どんなtypeで」コミットするかだけで、ブランチ保護とpushは毎回同じ手順でやればよいので、迷わず淡々と実行する。

## 全体の流れ

1. 現在の状態を確認する
2. 保護対象のブランチにいるなら、作業用ブランチを切る
3. コミットする内容をステージする
4. Conventional Commits形式でコミットする
5. pushできるならpushする
6. 結果を報告する

このうち **判断が要るのは1（何が対象か）・3（どのファイルか）・4（type と subject）だけ**で、2・5と実際のコマンド実行は完全に定型である。コミットはセッションの末尾で発生するため、この定型部分を膨らんだコンテキストのまま自分で実行すると、1回あたり数十万トークンをブランチ確認とpushに費やすことになる。

## 実行の委譲

`.claude/agents/git-committer.md` が存在する場合、**判断だけを自分で行い、実行はそのエージェントに委譲する**。

自分で行うこと（このセッションのコンテキストがないとできない）:

- 手順1: コミット対象になる変更があるか、それが何のための変更かの把握
- 手順3: 今回の変更として意図したファイルの特定（`git add -A` を避けるために必要）
- 手順4: 下の早見表による type の判定と、subject の文面

`Agent` ツールで `subagent_type: "git-committer"` を指定し、次を渡す:

- **コミットメッセージ全文** — 1行目、必要なら本文、末尾の `Co-Authored-By:` 行まで確定させて渡す。`Co-Authored-By` には**このセッションで実際に作業したモデル**を書く（エージェント側は文面を一字一句変えない）
- **ステージ対象のファイルパス一覧** — 明示的に列挙する
- ブランチ名（決めてあれば）、除外指定（検証用の一時生成物など、あれば）

返ってくるのはブランチ名・コミットハッシュ・push結果の3行なので、それをユーザーに伝えれば手順6は完了する。エージェントが停止して判断を求めてきた場合（秘密情報の混入、フックによる拒否、pushの拒否など）は、その内容をユーザーに報告する。

**委譲しない方がよい場合**: セッションを開いた直後で自分も差分の内容を知らない場合は、そもそもコンテキストが浅く委譲の利点が無いうえ、意図の把握のために結局差分を読む必要がある。その場合は以下の手順を自分で実行する。エージェントが存在しない場合も同様。

以下、各ステップの詳細。委譲する場合も、手順1・3・4の判断基準はこちらを読んで従う。

## 1. 現在の状態を確認する

`git status` と `git diff` / `git diff --staged` で、コミット対象になる変更があるかを確認する。

- 変更が何もない（working treeがclean）場合は、ここで終了する。ユーザーにその旨を伝え、空コミットは作らない。
- 何かコミット対象があるなら次に進む。

## 2. 保護対象のブランチにいるなら、作業用ブランチを切る

`git branch --show-current` で現在のブランチ名を取得する。

- 出力が `main` または `master` の場合 → 保護対象。新しいブランチを切る。
- 出力が空（detached HEAD状態）の場合 → これも保護対象として扱う。detached HEADのままコミットすると、ブランチに紐付かず後で辿れなくなり実質的にmain/masterへ直接コミットするのと同じくらい危ういため。
- それ以外のブランチ名（すでに作業用ブランチにいる）→ 新しいブランチは切らず、そのままステップ3へ。

新しいブランチを切る場合の手順:

1. 差分の内容から、下の「Conventional Commitsのtype早見表」を参考にtypeを1つ判定する。
2. 変更内容を要約した短い英単語スラッグ（小文字・ハイフン区切り、2〜4単語程度）を作る。例: `add-login-form`, `fix-null-pointer`。ブランチ名はツールやリモート間の互換性のため英数字とハイフンのみで構成し、日本語や記号は使わない。
3. ブランチ名を `<type>/<slug>` の形にする（例: `feat/add-login-form`）。
4. そのブランチ名がすでに存在する場合（`git branch --list <name>`で確認）、末尾に `-2`, `-3` のように連番を付けて衝突を避ける。
5. `git checkout -b <branch-name>` でブランチを作成する。

## 3. コミットする内容をステージする

`git add -A` や `git add .` のような無差別なステージングはしない。`git status` の出力を見て、今回の変更として意図したファイルだけを個別に `git add` する。

特に次の点に注意する:

- `.env` や認証情報ファイルなど、秘密情報を含みそうなファイルが変更/追加されていないか確認する。含まれている場合はステージせず、ユーザーに確認する。
- ステージ後に改めて `git status` / `git diff --staged` で、意図しないファイルが混ざっていないか確認する。

## 4. Conventional Commits形式でコミットする

コミットメッセージは次の形式にする。

```text
<type>[(<scope>)]: <subject>
```

- `type` は下の早見表から選ぶ。英語小文字で固定。
- `scope` は任意。変更が特定のディレクトリ/モジュールに閉じている場合、そのディレクトリ名などを括弧内に書く（例: `feat(skills): ...`）。全体に関わる変更や、scopeを絞る意味が薄い場合は省略してよい。
- `subject` はこのリポジトリのコミット履歴（`git log --oneline`）に合わせて日本語で簡潔に書く。「〜を追加」「〜を修正」のように体言止め/常体で、末尾の句点は付けない。

本文（bodyやfooter）が必要なほど複雑な変更であれば、subjectの後に空行を挟んで補足を書いてよい。単純な変更ならsubjectだけで十分。

コミットは必ずheredocでメッセージを渡す（改行やクォートの事故を避けるため）:

```bash
git commit -m "$(cat <<'EOF'
feat: ログイン画面を追加

Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>
EOF
)"
```

Co-Authored-By の行は、このセッションの標準的なコミット作法（Bashツールのcommit手順）に既に定められているので、それに従う。

### Conventional Commitsのtype早見表

| type | 使うタイミング |
| --- | --- |
| `feat` | 新機能・新しい振る舞いの追加 |
| `fix` | バグ修正 |
| `docs` | ドキュメントのみの変更（README, SKILL.md等） |
| `style` | 動作に影響しないフォーマット・空白・命名などの変更 |
| `refactor` | 機能追加でもバグ修正でもない、内部構造の整理 |
| `perf` | パフォーマンス改善 |
| `test` | テストの追加・修正 |
| `build` | ビルド周り・依存関係・パッケージ設定の変更 |
| `ci` | CI設定の変更 |
| `chore` | 上記のどれにも当てはまらない雑務的な変更 |
| `revert` | 過去のコミットの取り消し |

変更が複数のtypeにまたがる場合は、一番主要な意図（このコミットが何のために行われたか）で1つ選ぶ。無理に分割コミットにする必要はない。

## 5. pushできるならpushする

コミットが完了したら、破壊的な操作をせずにpushを試みる。

- 新しくブランチを作った場合（ステップ2を通った場合）: `git push -u origin <branch-name>` でupstreamを設定しながらpushする。
- 元から作業用ブランチにいて新規ブランチを作らなかった場合: まず `git push` を試す。upstreamが未設定なら同様に `-u origin <branch-name>` を付けて試す。

push時に次のような状況になったら、force pushや `--force-with-lease` などで無理に押し通さず、状況をそのままユーザーに報告して判断を仰ぐ:

- リモート `origin` が設定されていない、またはネットワーク的に到達できない
- 認証エラーで拒否される
- リモート側が進んでいて（diverged）、単純pushでは拒否される
- ブランチ保護ルールなどで拒否される

pushが飛ばされた・失敗した場合でも、ローカルのコミット自体は完了しているので、それはそれとして成功と報告する。

## 6. 結果を報告する

最後に、次を簡潔にまとめてユーザーに伝える:

- 新しいブランチを作ったか（作った場合はブランチ名）
- コミットハッシュとコミットメッセージ（1行目）
- pushの結果（成功/スキップ/失敗とその理由）

## このスキルの対象外

- コンフリクトの解消は行わない。pushやrebaseでコンフリクトが起きたら、その場で止まってユーザーに報告する。
- Pull Requestの作成はこのスキルの範囲外。pushまでが対象。PR作成が必要ならユーザーに別途確認する。
- force push、`git reset --hard`、hookのスキップ（`--no-verify`等）、コミットのamendは、ユーザーが明示的に指示しない限り行わない。
