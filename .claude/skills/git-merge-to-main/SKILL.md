# git-merge-to-main

作業ブランチが積み上がったまま放置される、ベースブランチが古いままマージされてコンフリクトの原因になる、マージ後に不要になったブランチが残り続ける——このスキルはその3つを機械的に防ぐためのものである。判断が要るのはコンフリクトや拒否が起きたときにどうするかだけで、それ以外は毎回同じ手順で淡々と進める。

## 全体の流れ

1. 現在の状態とマージ対象のブランチを確認する
2. ベースブランチ(main/master)を特定し、最新化する
3. ベースブランチに切り替えてマージする
4. push する
5. 統合済みの元ブランチを削除する(ローカル・リモート)
6. 結果を報告する

以下、各ステップの詳細。

## 1. 現在の状態とマージ対象のブランチを確認する

`git branch --show-current` で現在のブランチを確認し、`git status` で作業ツリーがクリーンかを確認する。

- 作業ツリーが汚れている(未コミットの変更がある)場合、そのままブランチを切り替えるとcheckoutが失敗するか、意図しない挙動になる可能性がある。ここで止まり、コミットするか(git-commitスキルの範囲)、stashするかをユーザーに確認する。
- マージ対象のブランチは、ユーザーが名指ししていればそれを使う。名指しがなければ、現在のブランチをマージ対象とみなす。ただし現在のブランチが後述のベースブランチそのものである場合、マージ対象が不明なので、どのブランチを統合したいかユーザーに確認する。

## 2. ベースブランチ(main/master)を特定し、最新化する

`git branch --list main` と `git branch --list master` でどちらが存在するかを確認する(両方存在するリポジトリは通常ないが、念のため)。ユーザーが明示的にベースブランチを指定した場合はそれを優先する。

`git fetch origin` した上で、ローカルのベースブランチが `origin/<base>` から遅れていないか確認する(`git log origin/<base>..<base>` などで先行コミットがないか、`git log <base>..origin/<base>` で追従できるかを見る)。

- ローカルが単純に追従できる(fast-forward可能)なら、ベースブランチを最新化してから次に進む。
- ローカルのベースブランチがoriginと分岐している(diverged)場合は、自動で解決しようとせず、状況をそのままユーザーに報告して判断を仰ぐ。

## 3. ベースブランチに切り替えてマージする

`git checkout <base>` でベースブランチに移動し、次のように `--no-ff` でマージする(マージコミットを必ず作り、統合の履歴を残す)。

```bash
git merge --no-ff <feature-branch> -m "$(cat <<'EOF'
Merge branch '<feature-branch>'
EOF
)"
```

もしGitHub上に対象ブランチのopenなPRが存在する場合(`gh pr list --head <feature-branch> --state open` で確認できる)、`gh pr merge` は使わず、このとおりローカルでマージする。ただしこの場合、GitHub側のPRはローカルマージによって自動ではクローズされない点に注意し、後述の結果報告でその旨をユーザーに伝える。

コンフリクトが発生した場合は自動解決を試みず、その場で止まってユーザーに状況(コンフリクトしているファイル一覧など)を報告する。`git merge --abort` で元に戻すかどうかもユーザーに委ねる。

## 4. push する

マージが完了したら `git push origin <base>` する。

push時に次のような状況になったら、force pushなどで無理に押し通さず、状況をそのままユーザーに報告して判断を仰ぐ:
- リモート `origin` が設定されていない、またはネットワーク的に到達できない
- 認証エラーで拒否される
- リモート側がさらに進んでいて(diverged)、単純pushでは拒否される
- ブランチ保護ルールなどで拒否される

## 5. 統合済みの元ブランチを削除する(ローカル・リモート)

push が成功したら、マージ元のブランチを削除する。

```bash
git branch -d <feature-branch>
git push origin --delete <feature-branch>
```

`-d`(小文字)は、そのブランチが完全にマージ済みでない場合は削除を拒否する安全弁になっている。これが拒否された場合は、意図せず未マージの変更が残っている可能性があるので、`-D` で強制削除せず、ユーザーに報告して判断を仰ぐ。

リモートブランチの削除は、削除して問題ないか判断がつかない場合(例:他の人がまだそのブランチを見ている可能性がある、CI設定がブランチ名に依存している等の兆候がある場合)は、実行前にユーザーに一声かける。

## 6. 結果を報告する

最後に、次を簡潔にまとめてユーザーに伝える:
- マージしたブランチ名とマージコミットのハッシュ
- push の結果(成功/スキップ/失敗とその理由)
- ローカル・リモートそれぞれのブランチ削除結果
- 対象ブランチにopenなPRが存在していた場合、ローカルマージではPRが自動クローズされない旨の注意

## このスキルの対象外

- コンフリクトの解消そのものは行わない。発生したら止まってユーザーに報告する。
- ベースブランチがoriginと分岐している場合の解決(rebaseやreset)は行わない。
- force push、`git reset --hard`、hookのスキップ(`--no-verify`等)は、ユーザーが明示的に指示しない限り行わない。
- コミット自体(まだマージ対象ブランチに変更がコミットされていない場合)はgit-commitスキルの範囲であり、このスキルはそこから先(統合・後片付け)を担当する。
