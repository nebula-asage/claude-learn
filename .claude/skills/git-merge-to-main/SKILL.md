# git-merge-to-main

作業ブランチが積み上がったまま放置される、ベースブランチが古いままマージされてコンフリクトの原因になる、マージ後に不要になったブランチやworktreeが残り続ける——このスキルはその3つを機械的に防ぐためのものである。判断が要るのはコンフリクトや拒否が起きたときにどうするかだけで、それ以外は毎回同じ手順で淡々と進める。

## 全体の流れ

1. worktree内にいる場合は一旦抜ける
2. 現在の状態とマージ対象のブランチを確認する
3. ベースブランチ(main/master)を特定し、最新化する
4. ベースブランチに切り替えてマージする
5. push する
6. 統合済みの元ブランチを削除する(ローカル・リモート。対応するworktreeがあればそれも削除する)
7. 結果を報告する

## 実行の委譲

この手順は**判断をほとんど含まない**（判断が要るのはコンフリクトや拒否が起きたときだけで、それは止まってユーザーに聞くと決まっている）。一方、マージはコミットと同じくセッションの末尾で発生するため、肥大化したコンテキストのまま自分で実行すると定型のgit操作に大量のトークンを費やすことになる。

委譲前に、手順1（worktree内にいる場合は一旦抜ける）は**トップレベルセッション自身が先に済ませておく**。`.claude/agents/git-merger.md` は禁止事項として「worktreeの作成・切り替え・削除」を明記しており、worktree絡みの操作は一切委譲できない。worktreeから抜けて本来の作業ディレクトリに戻り、抜けたworktreeのパスを覚えておいたうえで委譲する（手順6のworktree削除は委譲せず自分で行う）。

`.claude/agents/git-merger.md` が存在する場合、`Agent` ツールで `subagent_type: "git-merger"` を指定して委譲する。渡すのは次だけでよい:

- **マージ対象のブランチ名**（手順2の判断。ユーザーが名指ししていればそれ、無ければ手順1で抜けたブランチ、それも無ければ現在のブランチ）
- ベースブランチ名（`main`/`master` 以外を指定したい場合のみ）
- リモートブランチを削除してよいか（削除を避けたい事情がある場合のみ）

返ってくるのはマージ結果・push結果・ブランチ削除結果の4行なので、それをユーザーに伝える。ただし手順1でworktreeから抜けていた場合、対象ブランチはまだそのworktreeにチェックアウトされたままなので、`git-merger`のローカルブランチ削除は「別のworktreeでチェックアウト中」で失敗して停止する可能性が高い。これは想定内の中間状態であり、続けて手順6を自分で行えば完了する（手順7の報告はその後まとめて行う）。エージェントがその他の理由で停止して判断を求めてきた場合（作業ツリーが汚れている、ベースがoriginと分岐している、コンフリクト、pushの拒否）は、その内容をユーザーに報告して指示を仰ぐ。

エージェントが存在しない場合は、手順1・2・6・7に加えて `.claude/skills/git-merge-to-main/references/manual-steps.md` の手順3〜5も自分で実行する。

以下、各ステップの詳細（手順3〜5は委譲すれば読む必要が無いため `references/manual-steps.md` 側に分けてある）。

## 1. worktree内にいる場合は一旦抜ける

`git worktree list` の1行目は常にリポジトリ本来の作業ディレクトリ(`.git`が直接存在する場所)であり、それ以外の行が個別のworktreeである。カレントディレクトリが1行目と異なる場合、worktree内で実行していると判断する。

- このセッションが `EnterWorktree` で今のworktreeに入っている場合は、`ExitWorktree` を `action: "keep"` で呼んで本来の作業ディレクトリに戻る。**ここで `"remove"` を使ってはいけない**——`ExitWorktree` の `"remove"` はworktreeのディレクトリだけでなくブランチ自体も削除してしまうため、まだmainに統合していないこの時点で使うと変更ごと失う。
- `EnterWorktree` を経由していない場合(手動で`cd`した、サブエージェントとして作業ディレクトリを親と共有している等)は `ExitWorktree` の対象外になるので、`git worktree list` の1行目のパスへ`cd`して本来の作業ディレクトリに戻る。
- 元々worktree内にいない(本来の作業ディレクトリで実行している)場合、この手順は何もせず読み飛ばす。

worktree内にいた場合は、そのworktreeのパスとチェックアウトされていたブランチ名を手順6で使うために覚えておく。この時点ではworktreeのディレクトリ自体はまだ削除しない(ブランチがそこに残っていても、この後の手順2〜5には影響しない)。

## 2. 現在の状態とマージ対象のブランチを確認する

`git branch --show-current` で現在のブランチを確認し、`git status` で作業ツリーがクリーンかを確認する。

- 作業ツリーが汚れている(未コミットの変更がある)場合、そのままブランチを切り替えるとcheckoutが失敗するか、意図しない挙動になる可能性がある。ここで止まり、コミットするか、stashするかをユーザーに確認する。
- マージ対象のブランチは、ユーザーが名指ししていればそれを使う。名指しがなければ、手順1でworktreeから抜けた場合はそのworktreeでチェックアウトされていたブランチ、それも無ければ現在のブランチをマージ対象とみなす。ただし現在のブランチが後述のベースブランチそのものである場合、マージ対象が不明なので、どのブランチを統合したいかユーザーに確認する。

## 3〜5. ベースブランチの最新化・マージ・push

ベースブランチ(main/master)を特定して最新化し(originと分岐していれば止まって報告する)、`--no-ff` でマージし(コンフリクトが起きれば止まって報告する)、`git push origin <base>` する(拒否されれば止まって報告する)。具体的なコマンドと判断基準は `.claude/skills/git-merge-to-main/references/manual-steps.md` を参照する(委譲する場合はエージェントが同じ内容を実行するので読む必要はない)。

## 6. 統合済みの元ブランチを削除する(ローカル・リモート、worktreeも)

push が成功したら、マージ元のブランチを削除する。

手順1でworktreeから抜けていた場合、マージ対象のブランチはまだそのworktreeにチェックアウトされたままなので、先にworktree自体を削除する(ブランチの削除ではなく、worktreeという「チェックアウト先」を消すだけなので、この時点でmainへの統合が済んでいれば安全):

```bash
git worktree remove <worktree-path>
```

worktree内に未コミットの変更が残っている場合、このコマンドは失敗する。`--force`で押し通さず、状況をそのままユーザーに報告して判断を仰ぐ。

worktreeが無い、またはworktreeの削除に成功したら、通常どおりブランチを削除する。

```bash
git branch -d <feature-branch>
git push origin --delete <feature-branch>
```

`-d`(小文字)は、そのブランチが完全にマージ済みでない場合は削除を拒否する安全弁になっている。これが拒否された場合は、意図せず未マージの変更が残っている可能性があるので、`-D` で強制削除せず、ユーザーに報告して判断を仰ぐ。

リモートブランチの削除は、削除して問題ないか判断がつかない場合(例:他の人がまだそのブランチを見ている可能性がある、CI設定がブランチ名に依存している等の兆候がある場合)は、実行前にユーザーに一声かける。

## 7. 結果を報告する

最後に、次を簡潔にまとめてユーザーに伝える:

- マージしたブランチ名とマージコミットのハッシュ
- push の結果(成功/スキップ/失敗とその理由)
- ローカル・リモートそれぞれのブランチ削除結果
- worktreeから抜けた場合、そのworktreeの削除結果

## このスキルの対象外

- コンフリクトの解消そのものは行わない。発生したら止まってユーザーに報告する。
- ベースブランチがoriginと分岐している場合の解決(rebaseやreset)は行わない。
- force push、`git reset --hard`、hookのスキップ(`--no-verify`等)は、ユーザーが明示的に指示しない限り行わない。
- コミット自体(まだマージ対象ブランチに変更がコミットされていない場合)はこのスキルの対象外。このスキルはコミット済みの変更をマージする段階から先(統合・後片付け)を担当する。
- worktreeの新規作成(`EnterWorktree`)自体はこのスキルの対象外。既に存在するworktreeから抜け、統合後に不要になったworktreeを削除するところまでを担当する。
- worktree内に未コミットの変更や、マージ対象ブランチ以外へのコミットが残っている場合の解消は行わない。発生したら止まってユーザーに報告する。
