# git-merge-to-main: 手順3〜5の詳細（エージェントが存在しない場合）

`.claude/agents/git-merger.md` が存在しない場合に限り、以下の手動手順を実行する。エージェントに委譲する場合はエージェント自身が同じ内容を実行するため、このファイルを読む必要はない。

## 手順3. ベースブランチ(main/master)を特定し、最新化する

`git branch --list main` と `git branch --list master` でどちらが存在するかを確認する(両方存在するリポジトリは通常ないが、念のため)。ユーザーが明示的にベースブランチを指定した場合はそれを優先する。

`git fetch origin` した上で、ローカルのベースブランチが `origin/<base>` から遅れていないか確認する(`git log origin/<base>..<base>` などで先行コミットがないか、`git log <base>..origin/<base>` で追従できるかを見る)。

- ローカルが単純に追従できる(fast-forward可能)なら、ベースブランチを最新化してから次に進む。
- ローカルのベースブランチがoriginと分岐している(diverged)場合は、自動で解決しようとせず、状況をそのままユーザーに報告して判断を仰ぐ。

## 手順4. ベースブランチに切り替えてマージする

`git checkout <base>` でベースブランチに移動し、次のように `--no-ff` でマージする(マージコミットを必ず作り、統合の履歴を残す)。

```bash
git merge --no-ff <feature-branch> -m "$(cat <<'EOF'
Merge branch '<feature-branch>'
EOF
)"
```

GitHub上に対象ブランチのPRが存在するかどうかは確認しない。`gh pr merge` は使わず、常にこのとおりローカルでマージする。なお、対象ブランチにopenなPRが存在していた場合でも、ローカルマージによって自動ではクローズされない点に注意する必要はあるが、それを確認する手順自体は行わない。

コンフリクトが発生した場合は自動解決を試みず、その場で止まってユーザーに状況(コンフリクトしているファイル一覧など)を報告する。`git merge --abort` で元に戻すかどうかもユーザーに委ねる。

## 手順5. push する

マージが完了したら `git push origin <base>` する。

push時に次のような状況になったら、force pushなどで無理に押し通さず、状況をそのままユーザーに報告して判断を仰ぐ:

- リモート `origin` が設定されていない、またはネットワーク的に到達できない
- 認証エラーで拒否される
- リモート側がさらに進んでいて(diverged)、単純pushでは拒否される
- ブランチ保護ルールなどで拒否される
